# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository nature

This is **not** a software project — it is a personal Markdown knowledge base (Information Security / cybersecurity notes, coursework, SOC operations) authored in Obsidian and published via GitBook. There is no root-level build, lint, or test pipeline. The one exception is a self-contained Python automation project nested under `Work/Automações/Entregaveis/` (see below).

`Work/` is a **separate nested git repository** (`Work/.git`), independent from the repo root (`.git`). Treat changes inside `Work/` as belonging to a different repo when checking status/history or committing.

## Build, test, and lint commands

Only `Work/Automações/Entregaveis` has commands to run:

```bash
cd "Work/Automações/Entregaveis"

# Install dependencies
python -m pip install -r requirements.txt

# Run integration tests
python -m unittest _dev/test_integration.py

# Run a single test by pattern
python -m unittest _dev/test_integration.py -k test_get_dashboard

# Main report generation flow
uv run python gerar_apresentacao.py --cliente CLIENTE --data-inicio YYYY-MM-DD --data-fim YYYY-MM-DD
```

## High-level architecture

### 1) Knowledge-base layer (repository root)
- Published through a GitBook-style structure: `SUMMARY.md` is the canonical table of contents for navigation — keep it in sync whenever pages are added, removed, renamed, or moved.
- `README.md` (with YAML front matter) is the GitBook landing page.
- Content is organized into:
  - `readme-1/` — large structured handbook tree (cyberetico courses, fatec coursework, dfir)
  - `cyberetico/` — security/course notes and related materials
  - `knowlage/` — investigations, CYBER notes, personal/wireless notes
  - `obsidian/` and `Work/` — workspace notes and operational (SOC) documentation
  - `reports/` — generated reports and an "Orphaned Files" index

### 2) Automation layer (`Work/Automações/Entregaveis`)
A Python pipeline for SOC/client deliverable presentations (PPTX generation):
1. **Ingestion** (`app/api/ingestion.py`) — pulls data from Grafana, Artia, Stellar Cyber, and Zammad.
2. **Persistence** (`app/db/crud.py`) — writes normalized data into PostgreSQL via generated CRUD/upsert functions keyed off `TABLE_SPECS`.
3. **Payload + metrics assembly** (`app/presentation/generator.py`, `alert_metrics.py`) — computes monthly metrics and placeholder values.
4. **Presentation rendering** (`update_presentation.py`, `gerar_apresentacao.py`) — replaces template placeholders/charts and writes PPTX outputs.
- `_dev/` holds ad-hoc inspection/debug scripts (pptx shape scanning, token counting) — not part of the production flow.
- `ESTRUTURA.md` in this directory documents each module's responsibility in Portuguese.

## Key conventions

### Vault / Markdown conventions
- Obsidian is the authoring tool (see `.obsidian/community-plugins.json`): notable plugins are `dataview`, `waypoint`, `smart-connections`, `obsidian-git`. This explains recurring patterns:
  - `%% Begin Waypoint %% … %% End Waypoint %%` blocks in folder overview files are auto-generated by the Waypoint plugin — preserve them when editing those files.
  - ` ```ccard type: folder_brief_live``` ` blocks are Dataview/card-board queries — don't hand-edit their output.
  - `.smart-env/` directories are Smart Connections plugin data — do not treat as source content.
- Internal links use Obsidian wikilinks (`[[...]]`), often crossing folders.
- Top-level/section index notes commonly use YAML front matter (e.g. `description`, `icon`).

### Automation conventions (`Work/Automações/Entregaveis`)
- Environment variables load from `.env` (`.env.example` is the reference); use existing keys from `app/config.py` rather than inventing new ones.
- Ingestion functions return structured status payloads (`status`, `source`, `reason`/`error`, `persisted`) instead of raising on missing credentials — follow this pattern for new integrations.
- Database access goes through `app/db/crud.py` table APIs (`create_*`, `list_*`, `upsert_*`) — avoid ad-hoc SQL in feature modules.
- Metrics logic is month-key based (`YYYY-MM`), comparing current vs. previous month across ingestion and presentation modules.

### Stale governance files — do not follow
- `.github/AGENTS.md` and `.github/CLAUDE.md` (and their `Work/.github/` duplicates) describe a generic TypeScript/`pnpm`/Spec-Driven-Development workflow (`.factory/spec.md`, `pnpm lint`, `pnpm validate`, `skills/qa-verifier/`) that **does not exist in this repository**. They appear to be unmodified boilerplate. Ignore their build/test/workflow instructions; this file and direct repo inspection are authoritative.
